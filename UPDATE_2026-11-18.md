## 10. Исправлена ошибка длинных сообщений (`can't find end of the entity`)

**Симптом:** в Telegram приходит `Bad Request: can't find end of the entity starting at byte offset 4144` — сообщение с результатами поиска не доставляется.

**Причины (нашёл две):**
1. В `bot/handlers/search.py` длинная выдача резалась «вслепую»: `body[:3900]`, затем обрезка по `\n\n**`. Обрезка попадала внутрь `**жирного**` или `[ссылки](url)` → незакрытая сущность → Telegram отклоняет всё сообщение целиком.
2. Динамический текст вставлялся в Markdown без экранирования: название канала `TOP LEVEL JOB [топ вакансии для руководителей]`, ники с `_` (`@uiux_jobs`), команда `/find_resources` в тексте — всё это Telegram считает разметкой.

**Что сделано:**
- Новый модуль `bot/services/message_utils.py`: `split_message()` (нарезка только по границам строк, длинные строки-«простыни» режутся со снятием разметки), `escape_markdown()` (экранирование `_ * ` [ ]` в динамическом тексте), `has_broken_entities()` (валидатор «как Telegram»), `strip_markup()` (аварийный plain-text).
- `bot/services/vacancy_parser.py`: экранируются заголовок вакансии, название источника, сниппет, совпадения навыков, названия площадок и URL в блоке предупреждений; команды обёрнуты в code-span (`` `/find_resources` ``).
- `bot/services/search_assistant.py`: экранируются названия/описания каналов, агрегаторов и компаний в ответах `/find_resources` (там же был скрытый такой же баг из-за канала со скобками в названии).
- `bot/handlers/messaging.py`: `prepare_text()` + `safe_answer/safe_edit_text/send_long_message` — перед отправкой текст проверяется, при незакрытой разметке уходит обычным текстом (лучше без жирного шрифта, чем никак); при отказе Telegram — автоматический повтор без `parse_mode`.
- `bot/handlers/search.py`: выдача и подвал отправляются через `send_long_message` / `safe_answer`, клавиатура крепится к последнему сообщению, дисклеймер всегда в последней части.
- `main.py`: глобальный обработчик ошибок `@dp.error()` — пишет причину в лог и отвечает пользователю вместо «тишины».

## 11. Должность из резюме больше не обрезается до первого слова

**Симптом:** в резюме написано «Руководитель продукта», а бот сохраняет в профиль «Руководитель» (то же с «Менеджер проектов» → «Менеджер», «Начальник цеха» → «Начальник»). Поиск шёл по слишком широкой должности.

**Причина:** в `bot/services/file_extractor.py` хвост регулярки `ROLE_TITLE_REGEX` разрешался только через закрытый список предлогов — `по | отдела | департамента | направления | группы | службы | филиала | подразделения`. Всё остальное отбрасывалось, потому что хвост был необязательным (`?`).

**Что сделано:**
- Хвост должности теперь допускает существительное в родительном падеже: `_ROLE_TAIL_WORD` + стоп-лист `_ROLE_TAIL_STOP` (чтобы «в Яндексе», «5 лет», «финансы» не приклеивались). Каждая альтернатива обёрнута в `(?:...)` (`_ROLE_TAIL_UNIT`) — иначе связка «с» съедала пробел («по работе склиентами»).
- Добавлены `ROLE_ABBREVIATIONS` + `_find_abbreviation()`: `CEO/CTO/CFO/COO/CMO/CPO/CIO`, `Product Owner`, `Scrum Master`, `Head of X`, `Senior/Lead … Manager`. Из строки выбирается **самое раннее** совпадение (`_pick_title_candidate`), поэтому «Senior Product Manager» не превращается в «Product Manager», а «Технический директор (CTO)» — в «CTO».
- `is_probable_person_name()` снова не путает должности и навыки с ФИО: добавлен `_NOT_A_NAME_TOKENS` (`manager`, `owner`, `management`, `economics`, …). Раньше «Product Owner» считался именем и должность терялась, а «Product Management»/«Unit Economics» выпадали из навыков.
- Составные профессии (`инженер-программист`, `инженер-конструктор` и т.п.) стоят в словаре раньше «инженер».
- `repair_profile_values()` / `is_truncated_role()`: сохранённая должность из одного общего слова («Руководитель», «Менеджер», «Директор»…) при старте бота перечитывается из текста резюме — старые профили чинятся автоматически, перезагружать резюме не нужно.
- `bot/services/vacancy_parser.py`: блокировка API hh.ru больше не теряется молча — при не-200 в предупреждения добавляется «HTTP 403 — API hh.ru отклонил анонимный запрос (блокировка облачных IP)». Сейчас hh.ru действительно отдаёт 403 на любой User-Agent с облачных адресов, поэтому вакансий hh в выдаче нет.

## 14. Подключение более продвинутой бесплатной LLM (5 провайдеров + перебор)

**Задача:** дать боту модель посильнее для адаптации резюме, бесплатную.

### 14.1 Что было
Один-единственный эндпоинт из трёх переменных (`LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL`, по умолчанию Groq `llama-3.3-70b-versatile`), без перебора провайдеров, без Gemini (у него нативный протокол), без диагностики: при 429/401 бот молча уходил в локальный движок, и понять почему было нельзя.

### 14.2 Что сделано

Новый модуль **`bot/services/llm_client.py`**:
- `build_providers()` собирает провайдеров из окружения: `GEMINI_API_KEY` (нативный `:generateContent`, `x-goog-api-key`), `GROQ_API_KEY`, `CEREBRAS_API_KEY`, `MISTRAL_API_KEY`, `OPENROUTER_API_KEY` и универсальный `LLM_API_KEY` + `LLM_BASE_URL` + `LLM_MODEL` (годится для локальной Ollama `http://localhost:11434/v1`).
- Порядок: свой `LLM_*` → Gemini → Groq → Cerebras → Mistral → OpenRouter; переопределяется `LLM_ORDER`, единственный провайдер — `LLM_PROVIDER`; модели — `GEMINI_MODEL`, `GROQ_MODEL`, `CEREBRAS_MODEL`, `MISTRAL_MODEL`, `OPENROUTER_MODEL`.
- `generate_text()` перебирает провайдеров: `HTTP 429` («исчерпана бесплатная квота»), `401/403` («проверьте ключ»), `404` («модель недоступна»), таймаут, пустой ответ, ответ короче 400 символов и вежливый отказ («не могу помочь») → следующий провайдер. Возвращает `LLMResult(text, provider_label, model, attempts)` или `None`.
- Защита от переполнения контекста: `LLM_MAX_INPUT_CHARS` (16 000 символов, для Cerebras с 8K-контекстом ставится меньше), таймаут — `LLM_TIMEOUT` (75 с, для резюме 20 с из прошлой версии не хватало), `max_tokens=4000`.
- Промпт переписан: явный запрет выдумывать факты и цифры (`[уточнить: доля выручки]` вместо придуманной метрики), требование отдавать только готовое резюме в Markdown.

Интеграция:
- `market_standards.adapt_resume_to_market_standards`: в отчёте теперь честный движок — «🤖 Модуль обработки: **Бесплатная LLM: Groq (free tier) · llama-3.3-70b-versatile**»; в результат добавлен `llm_attempts`.
- `bot/handlers/resume.py`: если LLM настроена, но не ответила — в отчёте строка «⚠️ Бесплатная LLM не ответила (причины)»; если ключей вообще нет — подсказка «подключите бесплатную LLM, инструкция `/llm`».
- Новая команда **`/llm`** (`bot/handlers/common.py`): показывает подключённые модели, маскированные ключи, порядок перебора и результат последнего вызова; без ключей — пошаговая инструкция с ссылками на 5 провайдеров и именами секретов GitHub.
- `main.py`: при старте в лог пишется, какие LLM подключены.
- `run_bot.yml`: в env добавлены `GEMINI_API_KEY`, `GROQ_API_KEY`, `CEREBRAS_API_KEY`, `MISTRAL_API_KEY`, `OPENROUTER_API_KEY` (+ `*_MODEL`, `LLM_ORDER`, `LLM_PROVIDER`, `LLM_TIMEOUT`, `LLM_MAX_INPUT_CHARS`) — секрет из GitHub подхватывается без правок кода.
- `.env.example` и README (новый п. 3.1) — инструкция: где взять ключ, лимиты бесплатных тарифов на 18.11.2026, приватность (на free-тарифах данные могут идти в обучение — предупреждение вынесено явно).

## 16. Адаптированное резюме очищается от «признаков ИИ» (`##`, `**`, эмодзи, тире)

**Задача:** в результате адаптации убрать видимые следы генерации — в первую очередь `##` и `**`.

**Что сделано** — новый модуль `bot/services/text_cleanup.py` (`clean_ai_artifacts`, `has_markdown_artifacts`):
- снимается Markdown: заголовки `#`/`##`/`###` → строка ЗАГЛАВНЫМИ (русские слова апперкейсятся, латинские термины сохраняют регистр: «ПРОФИЛЬ (Executive Summary)»), `**`/`__`/`*`/`_`, обратные кавычки и блоки ``` ```, горизонтальные линии `---`;
- пункты `-`, `*`, `+` → «•»; markdown-таблицы `| a | b |` → «a • b»; ссылки `[текст](url)` → «текст (url)»;
- удаляются эмодзи и декоративные символы в начале строк («🎯 ЦЕЛЬ» → «ЦЕЛЬ»);
- вычищаются мета-фразы модели: «Конечно! Вот готовое резюме:», «Надеюсь, это поможет», «Если нужно — могу…», «Как видите», «Ниже представлено», строки «Примечание:», «Итог:»;
- длинное тире «—» нормализуется в «–» (типичный признак генерации), схлопываются лишние пробелы и пустые строки;
- `[уточнить: …]` **сохраняется** — это подсказка человеку, а не артефакт.

Где применено:
- `adapt_resume_to_market_standards`: чистка идёт один раз на выходе (и для LLM, и для встроенного движка), в `adapted_text` и в БД уходит чистый текст; `.docx` собирается из того же очищенного текста, разделы — стиль Heading 2 по заглавной строке, пункты — List Bullet.
- Промпт LLM дополнен теми же требованиями (без `#`, `**`, обратных кавычек и таблиц; разделы — заглавными; пункты — «•»; без длинных тире и вступлений), т.е. защита двойная: промпт + постобработка.
- `bot/handlers/resume.py`: текст адаптированного резюме уходит обычным текстом и режется через `split_message` вместо «слепых» `[:4000]`/`3800` (заодно закрыт старый TODO — обрезка рвала слова).

## 18. Поиск: выбор области (Telegram / сайты / карьерные страницы / везде) + дедупликация выдачи

**Меню поиска стало двухшаговым** (`bot/handlers/search.py`, `bot/keyboards.py`):

1. **Где искать** (`search_scope:*`) — в сообщении сразу счётчики источников:
   🌍 Везде · 📡 Только Telegram · 🌐 Только сайты и агрегаторы · 🏢 Только карьерные страницы компаний.
2. **Период** (`search_period:<дни>:<область>`) + кнопка «🎛 Изменить область поиска».
   Старый формат `search_period:7` без области считается поиском «везде» — старые кнопки в истории чата не ломаются.

**Классификация источников** — новый `bot/services/source_scopes.py`: `telegram` (t.me / tg_channel), `web` (сайты, API, ручные борды), `career` (career./job./rabota.-домены, пути /career, /vacancies, `source_type=career`, названия «Карьера: …»). Агрегаторы (`hh.ru`, `career.habr.com`, `budu.jobs`, `remoteok.com` и др.) принудительно остаются в `web`. В базе сейчас: **169 источников — 135 Telegram, 28 сайтов/агрегаторов, 6 карьерных страниц**.

**Карьерные страницы компаний**: добавлены VK, Avito, 2ГИС, МТС, Яндекс, X5 Group (`source_type="career"`, досеиваются в существующую БД). Новый парсер `parse_career_page_html()`: JSON-LD `JobPosting` → ссылки-вакансии, навигация («Все вакансии», «О компании») отбрасывается. Проверено на живом сайте: `scope=career` вернул 5 реальных вакансий VK Tech («Коммерческий директор Бизнес-приложения VK Tech» и др.). Страницы с вакансиями только в JS (Сбер, Т-Банк) отдают пусто — это ожидаемо.

**Дедупликация** — новый `bot/services/vacancy_dedup.py`, работает при **любом** поиске:
- дубль = совпал URL · совпали нормализованное название и компания · совпал длинный текст описания (≥120 симв., схожесть ≥0.88) при похожих названиях;
- из группы остаётся **один** вариант — самый релевантный, при равенстве самый свежий;
- **разные компании с одинаковым названием должности не склеиваются** (проверено тестом);
- в шапке: «🔁 Убрано N дублей (в выдаче — по одному варианту из каждой группы)», счётчик «📊 Найдено уникальных вакансий», строка «🎛 Область поиска: …».

**Проверено вживую:**
- `/search` → «📡 Источники в базе: всего 169 — 📡 Telegram 135, 🌐 сайты и агрегаторы 28, 🏢 карьерные страницы 6», 4 кнопки области;
